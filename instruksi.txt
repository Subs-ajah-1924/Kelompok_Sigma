================================================================================
0. PRINSIP KERJA
================================================================================

1. Selesaikan fitur inti dulu, baru poles tampilan. Jangan mengejar fitur
   tambahan sebelum CRUD, autentikasi, isolasi data, dan kanban stabil.
2. Semua data tugas, mata kuliah, dan agenda selalu terikat ke user yang
   sedang login. Tidak ada role admin.
3. Satu sumber kebenaran (single source of truth):
   - Status tugas hanya disimpan di kolom tasks.status.
   - Deadline tugas hanya disimpan di tasks.deadline.
   - Agenda manual hanya disimpan di tabel agendas.
   - Kalender TIDAK menyimpan salinan deadline tugas.
4. Semua input divalidasi di server. Validasi HTML di browser hanya bonus.
5. Semua perubahan data lewat controller + Form Request + Policy. Jangan
   mengandalkan JavaScript untuk keamanan.
6. UI harus ringan: server-rendered Blade, Tailwind, Alpine.js seperlunya,
   tanpa SPA framework, tanpa library kalender/chart yang berat.
7. Setiap fase harus punya bukti selesai: bisa didemokan, lolos test, dan
   tidak merusak fitur sebelumnya.
8. Gunakan bahasa Indonesia untuk teks UI, nama fitur, label status, dan
   alasan rekomendasi agar mudah dipresentasikan.


================================================================================
1. RINGKASAN PROYEK
================================================================================

Aplikasi web untuk mahasiswa mengelola:
- Akun pengguna (registrasi, login, logout).
- Mata kuliah milik masing-masing pengguna.
- Tugas dengan judul, deskripsi, mata kuliah, deadline, tingkat kesulitan,
  dan status pengerjaan.
- Kanban Board (To Do, In Progress, Done) yang tersinkron dengan status tugas.
- Rekomendasi prioritas deterministik berbasis aturan (tanpa AI/ML).
- Pencarian dan filter tugas yang bisa dikombinasikan.
- Notifikasi deadline (terlambat, hari ini, segera, dan 7 hari ke depan).
- Kalender bulanan dengan agenda manual dan deadline tugas otomatis.

Yang TIDAK perlu dibuat pada versi ini (hindari scope creep):
- Role admin, manajemen user, atau halaman khusus admin.
- AI/ML, chatbot, embedding, atau rekomendasi berbasis model.
- Realtime WebSocket/Pusher, chat, komentar, lampiran file, rich text editor.
- Integrasi email/WhatsApp/push notification. Notifikasi cukup halaman/panel
  di dalam aplikasi.
- Aplikasi mobile native. Cukup web responsif.
- Pembayaran, subscription, atau fitur sosial.

2.2. ALTERNATIF YANG MASIH WAJAR

a. Livewire 3 + Blade + Tailwind
   - Produktivitas tinggi untuk filter, modal, dan update status tanpa banyak

   - Sedikit lebih berat dan lebih "magic" daripada Blade + Alpine.
   - Pilih ini hanya jika tim sudah nyaman dengan Livewire.

b. Laravel + Inertia + Vue 3/React
   - Tidak disarankan untuk tugas ini karena menambah kompleksitas build,

     Vue/React dan tetap ingin SPA.

c. Laravel + Bootstrap 5
   - Boleh, tetapi jangan digabung dengan Tailwind. Bootstrap + jQuery +
     template admin (AdminLTE) membuat halaman lebih berat dan sulit
     dikustomisasi. Tailwind lebih disarankan.

2.3. YANG SEBAIKNYA DIHINDARI

- AdminLTE, SB Admin, tema marketplace yang penuh plugin.
- jQuery + Bootstrap + Tailwind sekaligus.
- FullCalendar untuk kalender bulanan sederhana (cukup grid Carbon + CSS).
- Chart.js/ApexCharts jika tidak ada kebutuhan grafik.
- Moment.js, lodash, icon font, Google Fonts dengan banyak weight.
- Rich text editor (TinyMCE/CKEditor) untuk deskripsi tugas. Cukup textarea.
- CDN untuk aset produksi. Bundle lewat Vite agar tidak bergantung internet.
- Menyimpan status di dua tempat (mis. kolom status + tabel kanban terpisah).
- Menyimpan deadline tugas sebagai agenda duplikat.

2.4. MENGAPA STACK INI RINGAN

- Halaman dirender di server; browser tidak perlu mengunduh SPA framework.
- Tailwind hanya mengirim class yang dipakai.
- Alpine.js hanya dipakai untuk interaksi kecil (modal, dropdown, konfirmasi).
- SortableJS dimuat kondisional hanya di halaman Kanban.
- Kalender dibuat sendiri dengan grid CSS + Carbon, tanpa library besar.
- Tidak ada WebSocket, Redis, queue, atau worker. Cukup PHP + database.
- Ikon SVG inline, font sistem, dan pagination server-side.

Target performa kasar:
- JavaScript awal < 100 KB (gzip) di luar halaman Kanban.
- CSS produksi < 50 KB (gzip).
- Tidak ada N+1 query; gunakan eager loading relasi course.
- Halaman daftar tugas maksimal 12 item per halaman.

4. ARSITEKTUR DAN STRUKTUR KODE
================================================================================

4.1. GAYA ARSITEKTUR

Gunakan arsitektur MVC Laravel yang sederhana, ditambah:
- Form Request  : validasi + otorisasi input.
- Policy        : aturan kepemilikan data.
- Service       : logika rekomendasi deterministik.
- Enum          : nilai status dan tingkat kesulitan.
- Query scope   : filter dan pencarian agar controller tetap ramping.
- Blade component: UI konsisten dan tidak duplikasi markup.

Jangan membuat repository pattern, domain layer, CQRS, event sourcing, atau
abstraksi berlebihan untuk proyek sekecil ini. Cukup rapi dan mudah diuji.

4.2. TANGGUNG JAWAB FILE

| File/Komponen                  | Tanggung jawab |
|--------------------------------|----------------|
| routes/web.php                 | Daftar route + middleware auth |
| Controller                     | Ambil data, panggil service, kembalikan view/JSON |
| Form Request                   | Validasi input dan aturan kepemilikan course |
| Policy                         | Cek user boleh melihat/mengubah data |
| Model                          | Relasi, cast, scope pencarian/filter |
| TaskRecommendationService      | Hitung skor, label prioritas, dan alasan |
| Blade layout                   | Navigasi, flash message, slot konten |
| Blade component                | Badge, card, modal, empty state, tombol |
| Seeder                         | Data demo 2 user untuk uji isolasi data |

4.3. ATURAN PENULISAN KODE

- Nama class, method, variabel: bahasa Inggris (konvensi Laravel).
- Teks UI dan alasan rekomendasi: bahasa Indonesia.
- Gunakan type hint dan return type.
- Gunakan enum cast, bukan string bebas.
- Gunakan `auth()->user()->tasks()` untuk query data user, bukan `Task::all()`.
- Gunakan eager loading: `with('course')` pada daftar tugas.
- Gunakan `paginate(12)->withQueryString()` untuk mempertahankan filter.
- Jangan menaruh query kompleks di Blade.
- Jangan menaruh logika rekomendasi di controller; panggil service.
- Setiap controller method yang mengubah data memakai Form Request + Policy.
- Hindari `DB::raw` kecuali benar-benar perlu.
- Jalankan Pint sebelum commit.

5. STRUKTUR DATABASE
================================================================================

5.1. ERD SEDERHANA

    users (1) -----< courses
      |                 |
      |                 | (opsional, satu course punya banyak task)
      |                 v
      |--------------< tasks >---- courses
      |
      |--------------< agendas

Keterangan:
- users 1:N courses, tasks, agendas.
- courses 1:N tasks. tasks.course_id boleh NULL jika mata kuliah dihapus.
- agendas TIDAK berelasi ke tasks. Deadline tugas tidak pernah disalin ke
  agendas; kalender menggabungkan dua sumber data saat ditampilkan.

5.2. TABEL users (bawaan Laravel/Breeze)

Kolom wajib: id, name, email (unique), password, timestamps.
Tidak perlu kolom role. Semua user setara.

5.3. TABEL courses

    id
    user_id        foreignId -> users.id, cascadeOnDelete
    name           string(100)
    code           string(20), nullable
    color          string(7), nullable  // contoh: #4F46E5
    timestamps

    unique(['user_id', 'name'])
    index(['user_id'])

Aturan:
- Nama mata kuliah unik per user, boleh sama antar user berbeda.
- color opsional untuk chip UI; validasi format hex.
- Menghapus course tidak menghapus task; set tasks.course_id menjadi NULL.

5.4. TABEL tasks

    id
    user_id        foreignId -> users.id, cascadeOnDelete
    course_id      foreignId -> courses.id, nullable, nullOnDelete
    title          string(150)
    description    text, nullable
    deadline       dateTime
    difficulty     string(10)   // mudah | sedang | sulit
    status         string(15)   // todo | in_progress | done
    timestamps

    index(['user_id', 'deadline'])
    index(['user_id', 'status'])
    index(['user_id', 'difficulty'])

Aturan:
- deadline wajib diisi.
- status default 'todo'.
- Deadline boleh berada di masa lalu (tugas terlambat/import data). UI harus
  menandainya sebagai terlambat, bukan menolak data.
- completed_at tidak wajib. Tambahkan hanya jika butuh statistik "selesai
  minggu ini"; jika tidak, cukup status.
- Jangan menyimpan prioritas di database. Prioritas dihitung saat dibutuhkan
  oleh TaskRecommendationService agar selalu mengikuti deadline terbaru.

5.5. TABEL agendas

    id
    user_id        foreignId -> users.id, cascadeOnDelete
    date           date
    start_time     time, nullable
    title          string(150)
    description    text, nullable
    timestamps

    index(['user_id', 'date'])

Aturan:
- Ini agenda manual: catatan, rencana kegiatan, atau rencana pengerjaan.
- Tidak ada task_id di tabel ini.
- Jika user ingin mengerjakan tugas pada tanggal tertentu, ia menulis agenda
  manual; deadline tugas tetap tampil terpisah dari tasks.deadline.
- Jangan pernah membuat agenda otomatis dari deadline tugas.

5.6. ENUM

TaskStatus (string backed enum):
- todo         => label "To Do"
- in_progress  => label "In Progress"
- done         => label "Done"

Difficulty (string backed enum):
- mudah  => bobot 1
- sedang => bobot 2
- sulit  => bobot 3

Gunakan cast di model Task:
    protected function casts(): array
    {
        return [
            'deadline' => 'datetime',
            'status' => TaskStatus::class,
            'difficulty' => Difficulty::class,
        ];
    }

5.7. RELASI MODEL

User:
- courses(): hasMany(Course)
- tasks(): hasMany(Task)
- agendas(): hasMany(Agenda)

Course:
- user(): belongsTo(User)
- tasks(): hasMany(Task)

Task:
- user(): belongsTo(User)
- course(): belongsTo(Course)->withDefault() atau nullable handling

Agenda:
- user(): belongsTo(User)

5.8. FACTORY DAN SEEDER

Factory state yang wajib ada:
- TaskFactory: todo, inProgress, done, overdue, dueSoon, hard, easy.
- CourseFactory: dengan color.
- AgendaFactory: tanggal hari ini/beberapa hari ke depan.

DemoSeeder harus membuat:
- 2 user: demo1@example.com dan demo2@example.com (password diketahui,
  mis. "password").
- 3 mata kuliah untuk user 1, 2 mata kuliah untuk user 2.
- Minimal 10 tugas user 1 dengan variasi status, kesulitan, dan deadline:

Jalankan:

5.9. MIGRASI

- Satu migration per tabel; jangan menumpuk semua di satu file.
- Foreign key wajib.
- Gunakan cascadeOnDelete untuk user_id.
- Gunakan nullOnDelete untuk course_id.
- Tambahkan index sesuai daftar di atas.
- Jangan mengubah migration lama setelah di-commit; buat migration baru.
- Jalankan `php artisan migrate:fresh --seed` hanya di lokal, bukan produksi.


================================================================================
6. AUTENTIKASI, OTORISASI, DAN KEAMANAN
================================================================================

6.1. AUTENTIKASI

- Gunakan Breeze: register, login, logout, reset password, verifikasi email
  (opsional), dan halaman profile.
- Semua route aplikasi memakai middleware 'auth', kecuali halaman auth.
- Setelah register/login, arahkan ke /dashboard.
- Setelah logout, arahkan ke halaman login.
- Jangan membuat role admin.
- Jangan menampilkan daftar user lain.

6.2. ISOLASI DATA (WAJIB)

Aturan mutlak:
- Semua query data memakai relasi user yang login.
  Contoh: $request->user()->tasks()->with('course')->latest()->paginate(12)
- Jangan pernah menerima user_id dari form untuk task/course/agenda.
  user_id diisi dari auth()->id() atau lewat relasi.
- Saat mengambil detail: gunakan route model binding, lalu Policy.
- Saat membuat/mengubah tugas: validasi course_id harus milik user yang login.

Contoh aturan validasi course_id di StoreTaskRequest/UpdateTaskRequest:

    Rule::exists('courses', 'id')->where(
        fn ($query) => $query->where('user_id', $this->user()->id)
    )

Tanpa aturan ini, user bisa menempelkan tugas ke mata kuliah milik user lain.

6.3. POLICY

TaskPolicy:
- viewAny: true (query tetap dibatasi ke user sendiri)
- view: $task->user_id === $user->id
- create: true
- update: $task->user_id === $user->id
- delete: $task->user_id === $user->id

CoursePolicy dan AgendaPolicy: pola yang sama.

Di controller:
    $this->authorize('update', $task);

Panggil di method show, edit, update, destroy, dan updateStatus.
Policy mengembalikan 403. Jika ingin menyembunyikan keberadaan data, gunakan
query ter-scope user + findOrFail sehingga hasilnya 404. Pilih satu pola dan
konsisten; untuk proyek ini 403 dari Policy sudah dapat diterima asal diuji.

6.4. VALIDASI DAN SANITASI

- Gunakan Form Request untuk semua input.
- Gunakan `$request->validated()`, bukan `$request->all()`.
- Blade otomatis meng-escape {{ }}; jangan memakai {!! !!} untuk input user.
- Deskripsi tugas berupa plain text. Jangan simpan HTML mentah.
- Batasi panjang input agar tidak ada data raksasa.
- Tanggal divalidasi format dan rentangnya.
- File upload tidak ada pada versi ini, jadi tidak perlu aturan file.

6.5. CHECKLIST KEAMANAN

[ ] CSRF token pada semua form (@csrf) dan header X-CSRF-TOKEN untuk fetch.
[ ] Password di-hash (bawaan Laravel, jangan pernah hash manual).
[ ] Session regenerate setelah login dan invalidate setelah logout (Breeze).
[ ] Rate limit login aktif (bawaan Breeze).
[ ] Semua route data memakai middleware auth.
[ ] Semua aksi ubah/hapus memakai Policy.
[ ] course_id divalidasi kepemilikannya.
[ ] Tidak ada user_id dari request.
[ ] Tidak ada data user lain di dashboard, notifikasi, kalender, atau Kanban.
[ ] Pesan error validasi tidak membocorkan data user lain.
[ ] APP_DEBUG=false di produksi.
[ ] .env tidak di-commit.
[ ] HTTPS di produksi.
[ ] Jangan menampilkan stack trace atau query ke pengguna.

6.6. PENGUJIAN KEAMANAN MINIMAL

- Guest membuka /tasks -> redirect ke /login.
- User A membuka /tasks/{id-milik-B} -> 403/404.
- User A mengirim course_id milik B saat membuat task -> 422.
- User A mengubah status task milik B -> 403/404.
- User A melihat kalender/notifikasi -> hanya data A.
- User A menghapus task B -> 403/404 dan data B tetap ada.

10. PENCARIAN DAN FILTER
================================================================================

10.1. PARAMETER QUERY

    q              -> kata kunci judul/deskripsi
    course_id      -> id mata kuliah milik user
    status         -> todo|in_progress|done
    difficulty     -> mudah|sedang|sulit
    deadline_from  -> YYYY-MM-DD
    deadline_to    -> YYYY-MM-DD
    sort           -> deadline|created_at|title (opsional)
    page           -> halaman

10.2. PERILAKU

- Semua filter digabung dengan AND.
- Search mencakup title dan description (case-insensitive sesuai collation).
- Filter course hanya menampilkan course milik user.
- Rentang deadline inklusif: dari awal hari deadline_from sampai akhir hari
  deadline_to.
- Kombinasi filter dipertahankan saat pagination (withQueryString).
- Tombol "Reset" menghapus semua query filter.
- Tampilkan badge jumlah filter aktif.
- Jika tidak ada hasil, tampilkan empty state + tombol reset.
- Search bar memakai debounce 300ms (Alpine) atau tombol cari; jangan
  mengirim request setiap ketikan tanpa debounce.
- Filter disimpan di URL agar bisa di-refresh/di-bookmark.

10.3. IMPLEMENTASI

Gunakan scope di model atau query builder:

    $query = $request->user()->tasks()->with('course');

    $query->when($filters['q'] ?? null, function ($q, $term) {
        $q->where(function ($sub) use ($term) {
            $sub->where('title', 'like', "%{$term}%")
                ->orWhere('description', 'like', "%{$term}%");
        });
    });

    $query->when($filters['course_id'] ?? null, fn ($q, $id) =>
        $q->where('course_id', $id)
    );

    $query->when($filters['status'] ?? null, fn ($q, $status) =>
        $q->where('status', $status)
    );

    $query->when($filters['difficulty'] ?? null, fn ($q, $difficulty) =>
        $q->where('difficulty', $difficulty)
    );

    $query->when($filters['deadline_from'] ?? null, fn ($q, $from) =>
        $q->where('deadline', '>=', Carbon::parse($from)->startOfDay())
    );

    $query->when($filters['deadline_to'] ?? null, fn ($q, $to) =>
        $q->where('deadline', '<=', Carbon::parse($to)->endOfDay())
    );

Catatan keamanan:
- course_id dan filter lain divalidasi, bukan langsung dari request.
- Hindari `%` dan `_` liar pada LIKE jika ingin hasil presisi; minimal batasi
  panjang q. Untuk kebutuhan tugas, LIKE sederhana cukup.
- Jangan memakai `orderByRaw` dengan input user.

10.4. UI FILTER

- Form GET di atas daftar tugas.
- Search input dengan ikon.
- Select mata kuliah, status, difficulty.
- Dua input tanggal (from/to).
- Tombol "Terapkan" dan "Reset".
- Di mobile, filter bisa dilipat dalam panel/drawer agar tidak memenuhi layar.

10.5. TEST FILTER

- course_id hanya course sendiri; course user lain -> 422/empty.
- status + difficulty + date range digabung benar.
- Pagination mempertahankan query.

11. ALGORITMA REKOMENDASI (TANPA AI)

11.1. INPUT

- difficulty: mudah=1, sedang=2, sulit=3.
- deadline: dihitung relatif terhadap now() di timezone Asia/Jakarta.
- status: hanya tugas selain done yang diberi rekomendasi.

11.2. SKOR URGENSI DEADLINE

Gunakan selisih hari kalender (startOfDay) dan cek apakah deadline sudah lewat.

    deadline sudah lewat (< now)          -> urgensi 3
    deadline hari ini / <= 1 hari lagi    -> urgensi 3
    2-3 hari lagi                         -> urgensi 2
    4-7 hari lagi                         -> urgensi 1
    > 7 hari lagi                         -> urgensi 0

11.3. SKOR TOTAL

    skor = bobot_kesulitan + urgensi_deadline
    rentang skor: 1 sampai 6

11.4. LABEL PRIORITAS

    Jika deadline sudah lewat          -> Prioritas Tinggi (paksa)
    Jika skor >= 5                     -> Prioritas Tinggi
    Jika skor 3 atau 4                 -> Prioritas Sedang
    Jika skor <= 2                     -> Prioritas Rendah

11.5. ALASAN (BAHASA INDONESIA)

Susun dari dua bagian:
- "Tingkat kesulitan {mudah/sedang/sulit}."
- Kondisi deadline:
  - lewat: "Deadline sudah terlewat {n} hari."
  - <= 1 hari: "Deadline kurang dari 24 jam lagi."
  - 2-3 hari: "Deadline tinggal {n} hari lagi."
  - 4-7 hari: "Deadline {n} hari lagi."
  - > 7 hari: "Deadline masih {n} hari lagi."

Contoh alasan:
- "Tingkat kesulitan sulit; deadline kurang dari 24 jam lagi."
- "Tingkat kesulitan sedang; deadline tinggal 3 hari lagi."
- "Tingkat kesulitan mudah; deadline masih 10 hari lagi."

Jangan memakai kalimat yang menakut-nakuti atau menyalahkan pengguna.

11.7. PSEUDOCODE

    public function recommend(Task $task): Recommendation
    {
        if ($task->status === TaskStatus::Done) {
            return Recommendation::done();
        }

        $difficultyScore = match ($task->difficulty) {
            Difficulty::Easy => 1,
            Difficulty::Medium => 2,
            Difficulty::Hard => 3,
        };

        $now = now();
        $deadline = $task->deadline;
        $isOverdue = $deadline->lt($now);
        $days = $now->copy()->startOfDay()
            ->diffInDays($deadline->copy()->startOfDay(), false);

        $urgency = match (true) {
            $isOverdue => 3,
            $days <= 1 => 3,
            $days <= 3 => 2,
            $days <= 7 => 1,
            default => 0,
        };

        $score = $difficultyScore + $urgency;

        $priority = match (true) {
            $isOverdue => Priority::High,
            $score >= 5 => Priority::High,
            $score >= 3 => Priority::Medium,
            default => Priority::Low,
        };

        return new Recommendation(
            priority: $priority,
            score: $score,
            reason: $this->buildReason($task, $days, $isOverdue),
        );
    }

# Spesifikasi Fitur Web Task & Note Manager

## 1. Dashboard

### 1.1. Authentication
Buat sistem autentikasi pengguna yang mencakup registrasi, login, dan logout.
Aplikasi tidak menggunakan sistem role Admin karena seluruh pengguna memiliki
hak akses sebagai user. Setiap pengguna hanya dapat melihat, membuat,
mengubah, dan menghapus data miliknya sendiri. Pastikan semua akses data
dilindungi dengan autentikasi dan otorisasi yang sesuai.

### 1.2. Manajemen Tugas (Task Management)
Buat fitur CRUD (Create, Read, Update, Delete) untuk mengelola tugas. Setiap
tugas memiliki judul, deskripsi, mata kuliah, deadline, tingkat kesulitan,
dan status pengerjaan. Pengguna dapat menambahkan, mengubah, melihat detail,
serta menghapus tugas. Pengguna juga dapat membuat dan mengelola daftar mata
kuliah sendiri, kemudian menghubungkannya dengan tugas yang relevan.

### 1.3. Status Tugas dan Kanban Board
Sediakan tampilan Kanban Board untuk memvisualisasikan progres tugas
berdasarkan status, seperti To Do, In Progress, dan Done. Pengguna dapat
memindahkan tugas antarstatus dengan mudah. Status pada Kanban Board harus
tersinkronisasi dengan data tugas sehingga perubahan status langsung
tercermin pada tampilan lain di aplikasi.

### 1.4. Rekomendasi Pengerjaan Tugas
Buat fitur rekomendasi pengerjaan tugas menggunakan logika berbasis aturan,
tanpa AI atau model machine learning. Rekomendasi mempertimbangkan tingkat
kesulitan dan sisa waktu menuju deadline. Sistem memberikan label atau
indikator seperti prioritas tinggi, sedang, dan rendah, disertai alasan yang
mudah dipahami. Contohnya, tugas yang sulit dan memiliki deadline dekat dapat
ditandai sebagai tugas yang perlu mendapat perhatian lebih. Fitur ini hanya
memberikan rekomendasi, bukan menentukan urutan pengerjaan secara otomatis.

### 1.5. Pencarian dan Filter Tugas
Sediakan search bar untuk mencari tugas berdasarkan judul atau kata kunci.
Tambahkan filter berdasarkan mata kuliah, status pengerjaan, tingkat
kesulitan, dan rentang deadline. Pengguna dapat menggabungkan beberapa filter
sekaligus dan menghapus filter untuk kembali melihat seluruh tugas miliknya.

### 1.6. Notifikasi Deadline
Buat halaman atau panel notifikasi yang menampilkan daftar tugas berdasarkan
kedekatan deadline, termasuk tugas yang akan segera jatuh tempo dan tugas yang
sudah terlambat. Informasi yang ditampilkan mencakup judul tugas, mata kuliah,
tanggal deadline, dan status pengerjaan. Notifikasi harus diperbarui
berdasarkan data tugas terbaru dan tidak menampilkan tugas milik pengguna lain.

## 2. Kalender

### 2.1. Kalender Visual dan Agenda
Buat kalender berbentuk kotak-kotak dengan tampilan bulanan sebagai tampilan
utama. Pengguna dapat berpindah antarbulan dan memilih tanggal tertentu untuk
menambahkan, melihat, mengubah, atau menghapus agenda berupa teks, rencana
kegiatan, maupun rencana pengerjaan tugas. Agenda yang dibuat pengguna harus
dapat dibedakan secara visual dari deadline tugas otomatis.

### 2.2. Integrasi Deadline Tugas
Integrasikan kalender dengan data tugas. Setiap tugas yang memiliki deadline
otomatis ditampilkan pada tanggal yang sesuai tanpa perlu dimasukkan kembali
secara manual. Informasi deadline ditampilkan menggunakan indikator visual dan
dapat diklik untuk membuka detail tugas. Apabila deadline tugas diubah atau
tugas dihapus, tampilan kalender harus ikut diperbarui secara otomatis.

## 3. Ketentuan Umum Pengembangan

- Gunakan Laravel sebagai framework utama aplikasi.
- Gunakan database relasional untuk menyimpan akun, tugas, mata kuliah, dan
  agenda kalender.
- Terapkan validasi pada seluruh input pengguna.
- Pastikan data setiap pengguna terisolasi dan tidak dapat diakses oleh
  pengguna lain.
- Gunakan antarmuka yang responsif untuk desktop maupun perangkat mobile.
- Hindari fitur berbasis AI terlebih dahulu. Rekomendasi tugas menggunakan
  logika deterministik yang dapat dijelaskan dan diuji.
- Jaga konsistensi data antara dashboard, Kanban Board, notifikasi, dan
  kalender.
- Pisahkan agenda kalender yang dibuat manual dari deadline yang berasal dari
  tugas agar tidak terjadi duplikasi data.
- Prioritaskan fungsionalitas inti, kemudahan penggunaan, keamanan, dan
  struktur kode yang mudah dikembangkan sebelum menambahkan fitur lanjutan.

LAMPIRAN C - REKOMENDASI RINGKAS UNTUK PRESENTASI
================================================================================

Stack yang dipakai:
- Laravel 13 + PHP 8.4
- MariaDB 11.4 / MySQL 8
- Blade + Tailwind CSS 4 + Alpine.js
- SortableJS untuk Kanban
- PHPUnit + Laravel Pint
- Vite + Node 24

Alasan memilih:
1. Sesuai ketentuan Laravel dan database relasional.
2. Server-rendered + Tailwind membuat UI ringan dan cepat.
3. Breeze menyediakan autentikasi aman tanpa membangun dari nol.
4. Alpine + SortableJS cukup untuk interaksi tanpa SPA framework.
5. Kalender dibuat custom dengan Carbon, tanpa library berat.
6. Rekomendasi deterministik mudah dijelaskan, diuji, dan dipresentasikan.
7. Tidak butuh Redis, queue, WebSocket, atau layanan AI.
8. Mudah di-deploy ke VPS/shared hosting biasa.

Fitur yang ditonjolkan saat demo:
- Isolasi data dua akun.
- Drag & drop Kanban yang tersinkron.
- Rekomendasi + alasan yang bisa dijelaskan.
- Filter kombinasi + reset.
- Notifikasi deadline berkelompok.
- Deadline otomatis di kalender, terpisah dari agenda manual.
- Tampilan responsif di ponsel.
